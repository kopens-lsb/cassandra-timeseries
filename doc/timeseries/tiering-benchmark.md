# 계층형 저장(tiering) 벤치마크 — 1억 건, 전/후 비교

측정일 2026-07-31 · 이미지 `cassandra-timeseries:6.0.0` (SP3 투명 읽기 포함 빌드) · 단일 노드 컨테이너
(힙 16G, Generational ZGC) · 데이터: 보관 중인 스케일 데이터셋 재사용(1,000 시리즈 × 100,000행
= 1억 행, 1초 간격, 풀정밀 사인+톱니 값), 계층화는 **데이터셋 사본** 위에서 수행(원본 보존).
스크립트: [`docker/tiering-bench.sh`](../../docker/tiering-bench.sh) · 원시 리포트:
[베이스라인](tiering-bench-baseline.md) · [계층화 후](tiering-bench-tiered.md).

정책: `{"hot_window":"1h","chunk_window":"1h","interval":"7d"}` — 데이터가 전부
과거(2024-01-01 기준)라 **전 창이 콜드**가 되는 최대 부하 시나리오다. `gc_grace_seconds=0` +
메이저 컴팩션으로 레인지 톰스톤을 실제 회수해 저장량을 쟀다(단일 노드 벤치 설정).
(측정 당시 정책에는 `"codec":"auto"`가 있었다 — 창마다 Gorilla/Chimp128 중 작은 쪽을 골랐다.
그 옵션은 이후 [Chimp128 단일 코덱으로 통합](codec-bakeoff.md)되며 제거됐으므로, 지금 빌드로
같은 벤치를 돌리면 저장량 수치는 다시 재야 한다. 위 수치는 통합 이전 실측이다.)

## 요약

| 항목 | 계층화 전 | 계층화 후 | 변화 |
| --- | --- | --- | --- |
| 베이스 테이블 live bytes | 1.47 GB (LZ4 SSTable) | **0 B** (SSTable 0개) | 전량 청크화 |
| 청크 테이블 live bytes | — | **0.70 GB** (SSTable 1개, 28,000청크) | **2.1× 절감**, 7.0 B/sample |
| 데이터 디렉토리 | 1.7 GB | 1.1 GB | −35% |
| 재인코딩 (1억 행 → 28,000창) | — | **377 s** | **265k rows/s**, 74 windows/s |
| 톰스톤 회수 메이저 컴팩션 | — | 126 s | — |

> 압축률 해석: 이 데이터셋의 값은 **풀정밀 double**(사인+톱니) — XOR 계열 코덱의 최악 조건이다
> (7.0 B/sample은 [bake-off](codec-bakeoff.md)의 풀정밀 워크 측정과 일치). 실제 산업 데이터처럼
> 양자화된 값(0.1 단위 등)이면 bake-off 기준 0.25~1.45 B/sample — **LZ4 로우 대비 10배 이상**
> 절감이 코덱 수준에서 확인돼 있다.

## 질의 시간 (투명 읽기 — 동일 CQL, 동일 결과값, 2패스 중 웜 패스)

모든 질의의 **결과값이 전/후 완전 동일**함을 리포트의 first-result-row로 교차 확인했다
(percentile·histogram·approx_count_distinct까지 일치).

| 질의 (단일 파티션 = 10만 행) | 전 | 후 | 배속 |
| --- | --- | --- | --- |
| count(*) | 329 ms | **39 ms** | 8.4× |
| time_bucket 1h + avg/min/max | 524 ms | **78 ms** | 6.7× |
| time_bucket 5m + avg | 437 ms | **60 ms** | 7.3× |
| first/last/delta/rate per hour | 471 ms | **100 ms** | 4.7× |
| percentile p50/p95/p99 | 415 ms | **83 ms** | 5.0× |
| variance/stddev | 300 ms | **44 ms** | 6.8× |
| histogram 20버킷 | 311 ms | **51 ms** | 6.1× |
| integral + time_weighted_average | 336 ms | **64 ms** | 5.3× |
| gapfill 1h + locf (전 구간) | 410 ms | **60 ms** | 6.8× |
| 대시보드(OHLC+p95, 시간별) | 512 ms | **150 ms** | 3.4× |

| 멀티 파티션 | 전 | 후 | 배속 |
| --- | --- | --- | --- |
| 10 시리즈 시간별 avg (100만 행) | 4,086 ms | **565 ms** | 7.2× |
| 100 시리즈 시간별 avg (1,000만 행) | 39,866 ms | **5,600 ms** | 7.1× |
| 100 시리즈 p95 | 31,641 ms | **4,971 ms** | 6.4× |

빨라지는 이유: 파티션당 10만 행의 SSTable 순회 대신 **28개 청크(합 ~0.7MB)를 읽어 디코드**하기
때문이다. IO·역직렬화가 지배적인 시계열 집계에서 청크화가 읽기까지 이기는 결과다.

## 한계(정직하게)

- **파티션 키 없는 범위 스캔은 병합하지 않는다** — 핫 로우만 보이며(전량 청크화 시 0행),
  클라이언트 경고(`range scans read hot rows only...`)가 붙는다. v1 스코프(스펙 §3.3) —
  파티션+시간범위가 산업 주력 패턴이라는 전제. 풀스캔 결과가 필요한 운영 작업은 청크 테이블을
  함께 보거나 시리즈 목록으로 IN 질의를 구성한다.
- 병합 질의가 **한 페이지를 넘으면** 명확한 에러+힌트로 실패한다(침묵 중복/유실 방지).
  집계는 서버 내부 페이징이라 해당 없음.
- 디코드 로우의 `writetime(value)`은 청크의 `max_row_writetime` 근사값.
- 단일 노드 측정 — 멀티노드(3노드) 검증은 별도 이연 항목.
- 쓰기 경로는 계층화와 무관하게 동일(INSERT는 항상 베이스 테이블로, 재인코딩은 백그라운드)이라
  이번 측정에서 별도 쓰기 벤치는 생략했다. 재인코딩 자체의 부하는 위 377s(1억 행) 측정이 근거.
