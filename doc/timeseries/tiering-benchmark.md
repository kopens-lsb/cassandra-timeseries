## 질의 시간

같은 CQL, 같은 결과값. 비율은 `전 ÷ 후` — 1보다 크면 계층화가 빠릅니다.

### 집계 — 계층화가 빠릅니다

| 질의 (단일 파티션, 50,000행) | 비계층 | 계층화 | 비율 |
| --- | --- | --- | --- |
| `time_bucket 1h + avg/min/max` | 371 ms | **106 ms** | **3.50×** |
| `time_bucket 5m + avg` | 352 ms | **97 ms** | **3.63×** |
| `first`/`last`/`delta`/`rate` per hour | 370 ms | **114 ms** | **3.25×** |
| `derivative` per hour | 345 ms | **95 ms** | **3.63×** |
| `percentile` p50/p95/p99 | 306 ms | **78 ms** | **3.92×** |
| `variance`/`stddev` | 290 ms | **66 ms** | **4.39×** |
| `histogram` 20버킷 | 290 ms | **67 ms** | **4.33×** |
| `approx_count_distinct` | 307 ms | **75 ms** | **4.09×** |
| `OHLC + change + p95` (대시보드 종합) | 406 ms | **125 ms** | **3.25×** |
| `count(*)` (파티션 내) | 318 ms | **102 ms** | **3.12×** |
| 컬럼 존재 확인 (boolean 태그) | 362 ms | **124 ms** | **2.92×** |
| 컬럼 존재 확인 (double 태그) | 371 ms | **120 ms** | **3.09×** |
| `integral + time_weighted_average` | 4,941 ms | **3,670 ms** | 1.35× |

| --- | --- | --- | --- |

빨라지는 이유는 스캔량입니다 — 5만 행을 SSTable에서 훑는 대신 창당 청크 하나를 읽어 디코드합니다.
데이터가 4.9× 작아지므로 IO·역직렬화가 지배적인 집계에서 그대로 이득이 됩니다.

### 시간 범위를 걸지 않은 질의 — 계층화가 느립니다

느려지는 질의는 "행 단위"라서가 아니라 **시간 범위가 없어서** 느립니다. 측정값이 그대로 보여줍니다:

| 질의 | 시간 범위 | 비계층 | 계층화 | 비율 |
| --- | --- | --- | --- | --- |
| 1시간치 `timestamp+value`만 투영 | **있음** | 57 ms | **34 ms** | **1.68×** |
| 1시간치 `timestamp+value_numeric`만 투영 | **있음** | 56 ms | **33 ms** | **1.70×** |
| 1시간치 `SELECT *` (3,600행) | **있음** | 164 ms | 153 ms | 1.07× |
| 최신 1,000행 `SELECT *` (boolean 태그) | **없음** | 45 ms | 144 ms | **0.31× (3.2배 느림)** |
| 최신 1,000행 `SELECT *` (double 태그) | **없음** | 43 ms | 144 ms | **0.30× (3.3배 느림)** |
| **static 컬럼만 1행** | **없음** | 4 ms | 44 ms | **0.09× (11배 느림)** |

같은 `SELECT *`인데 시간 범위가 있는 쪽은 동률이고, 없는 쪽만 3배 느려집니다. 범위를 걸고 컬럼까지
좁히면 오히려 **1.7배 빨라집니다.**

**이유: 측정 당시에는 시간 범위가 없으면 그 파티션의 청크를 전부 디코드했습니다.** 범위를 걸면
해당 창의 청크만 풀면 되지만, 없으면 13.9시간치 = 창 14개를 모두 풀어야 했습니다. 당시에는
**`LIMIT`도 도움이 되지 않았습니다** — 디코드가 끝난 뒤에 적용되기 때문입니다. (이 병목은 측정
이후 창 단위 지연 디코드로 해소되었습니다 — 아래 참고.)

`static` 컬럼만 읽는 질의(4 ms → 44 ms)도 같은 이유입니다. static은 청크화되지 않아 디코드할 값이
없지만, 클러스터링 제한이 없으니 병합이 파티션의 모든 청크를 훑었습니다. 비계층에서 4 ms로 끝나던
질의라 비율이 11배로 커 보이지만 절대값은 44 ms입니다.

> **운영 규칙: 계층화된 테이블에는 항상 시간 범위를 거십시오.**
>
> ```sql
> -- 느림: 파티션의 청크 전부를 디코드
> SELECT * FROM pp.tm_tag_point WHERE tag_id='TAG-001' LIMIT 1000;
>
> -- 빠름: 해당 창의 청크만 디코드
> SELECT * FROM pp.tm_tag_point WHERE tag_id='TAG-001'
>   AND timestamp >= '2026-07-01 00:00:00+0000' AND timestamp < '2026-07-01 01:00:00+0000';
> ```
>
> 태그 메타데이터만 필요하다면 클러스터링을 좁혀 static을 읽는 편이 낫습니다.
> `LIMIT`으로 청크를 가지치기하는 최적화(DESC 질의에서 최신 창부터 디코드하고 조기 종료)는
> 이 측정 **이후 구현되었습니다**: 창 목록을 payload 없이 나열해 두고, 질의 방향 순서로(DESC면
> 최신 창부터) 한 창씩 페치·디코드하므로 `LIMIT`이 채워지면 나머지 창은 읽지 않습니다. 위 표의
> "없음" 행 수치는 구현 전 측정값입니다. `LIMIT` 없는 전체 스캔과 집계는 의미상 당연히 모든 창을
> 디코드합니다 — 시간 범위를 거는 편이 여전히 낫습니다.

## ⚠️ 파티션 키 없는 집계는 실제 행 수를 돌려주지 않습니다

| 질의 | 전 | 후 |
| --- | --- | --- |
| `SELECT count(*)` (파티션 키 없음) | 162,423 ms → `30000000` | **19 ms → `600`** |

**가속이 아니라 오답입니다.** 레인지 스캔은 청크를 병합하지 않으므로, 전부 계층화된 테이블에서
파티션 키 없는 집계는 **클러스터링 행을 하나도 보지 못합니다.** 여기서 나온 `600`은 태그 수입니다 —
static 컬럼은 청크화되지 않아 태그마다 static 행 하나가 남고, 그것만 세어진 값입니다.

> **`0`보다 위험합니다.** 0이면 뭔가 잘못됐다는 게 바로 보이지만, `600`은 "태그가 600개니까
> 맞나?" 싶은 그럴듯한 숫자입니다. static 컬럼이 없는 테이블에서는 `0`이 나옵니다 — 어느 쪽이든
> 실제 행 수(30,000,000)와는 무관합니다. 클라이언트 경고가 나가지만 대부분의
드라이버는 노출하지 않습니다. 투입 전 애플리케이션 점검 항목입니다 —
[프로덕션 체크리스트](production-rollout.md).

## 해석

이 형태에서 계층화는 **저장과 집계 양쪽에서 이깁니다** — 디스크 4.9×, 집계 3~4×, gap-fill 4.3~4.7×.
컬럼이 여럿이고 그중 상당수가 상수이거나 전부 null인 구조(`quality`·`error_code`·`attribute` 고정,
static `type`에 따라 `value_numeric`/`value_boolean` 중 하나가 통째로 빔)에서 컬럼 지향 청크가
설계 의도대로 동작한 결과입니다.

대가는 **시간 범위를 걸지 않은 질의**입니다. 범위 없는 `SELECT ... LIMIT N`은 측정 당시 파티션의
청크를 전부 풀었기 때문에 3배 느렸습니다(이후 창 단위 지연 디코드가 구현되어 `LIMIT` 질의는 필요한
창만 디코드합니다). 같은 질의라도 범위를 걸면 오히려 조금 빨라집니다.

> **`hot_window` 안쪽 질의는 비용이 없습니다.** 질의 범위가 콜드 경계 위에서 시작하면 병합 자체를
> 건너뛰고 핫 이터레이터를 그대로 돌려줍니다. 위 수치는 `hot_window 1h`로 **전 구간을 콜드로 만든**
> 최대 부하 조건입니다. 실제 운영에서 `hot_window`를 대시보드 구간에 맞추면 그 구간 질의는 계층화
> 전과 동일합니다.

## 형태에 따라 결과가 크게 다릅니다

같은 코드로 `(series text, ts timestamp, value double)` — **고엔트로피 double 컬럼 1개**짜리 형태를
재면 디스크 35% 절감에 질의는 동률~30% 느림이 나옵니다. 접을 상수 컬럼도, 비울 null 컬럼도 없어
컬럼 지향 포맷의 이득이 전혀 발생하지 않기 때문입니다.

**계층화의 이득은 "컬럼이 여러 개이고 그중 상당수가 반복적인가"에 달려 있습니다.** 산업 현장의
태그 테이블은 대체로 그렇지만, 도입 전 자기 테이블 형태로 재보는 편이 확실합니다.
