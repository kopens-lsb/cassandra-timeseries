# 읽기 경로 재설계 — 스냅샷을 버리고 스트리밍으로

**목표:** 컬럼 저장 memtable의 읽기 비용을 O(파티션 재구축)에서 O(log n + 반환 행 수)로 낮추되,
**읽기가 아무것도 보유(retain)하지 않게** 한다.

**한 줄 원칙:** 읽기는 스트리밍한다. 물질화(materialise)하지 않고, 캐시하지 않고, 보유하지 않는다.

---

## 0. 왜 재설계인가 — 두 번의 실패가 각각 남긴 제약

이 설계의 제약은 이론이 아니라 2026-08-02 프로덕션에서 실측된 실패다.

| 실패 | 원인 | 남긴 제약 |
| --- | --- | --- |
| **v1: 페이징 읽기 장애** (11:36, 11분) | `mayContainRowsIn`이 memtable 소유 `NativeClustering`으로 `ClusteringBound`를 제작 → offheap 할당에서 UOE. 인프로세스 테스트는 페이징도 native 할당도 안 함 | ① 읽기 경로는 **fail-open** — 판단 불가면 최적화 포기, 절대 예외 금지. ② **offheap + 네이티브 페이징 테스트가 게이트** |
| **v2: OOM 스파이럴** (18:59~19:47) | 증분 스냅샷이 샤드-파티션마다 `ImmutableBTreePartition` 전체를 **쓰기 중에도 무제한 보유** → 6시간에 걸쳐 16 GB 힙 고갈, flush 적체 451건 | ③ 읽기 경로는 **아무것도 보유하지 않는다** — "상한 있는 캐시"조차 다음 순위. ④ **소크형 힙 테스트가 게이트** — 6시간짜리 누수는 128회 반복 단위 테스트가 못 본다 |

v2가 풀려던 문제 자체는 실재한다: 쓰기마다 스냅샷을 무효화하면 다음 읽기가 파티션 전체를
BTree로 재조립한다 — 운영 실측 0.88 → 7.5 ms. **문제는 진짜였고, 해법이 틀렸다.**

살아남은 것(유지): comparator 직접 비교식 샤드 가지치기(제작 없음·보유 없음·fail-open),
지연 청크 디코드(창 카운터로 검증 완료), 그리고 이번에 만들어진 offheap·페이징 테스트들.

## 1. 0단계 — master 격리 해제 (재설계와 독립, 즉시)

master는 현재 v2(누수)를 담고 있어 배포 격리 상태다. 재설계 구현을 기다리지 말고 먼저:

- `TimeSeriesColumnarPartition`에서 **`lastSnapshot` 보유를 제거**한다 — 쓰기가 스냅샷을
  무효화하던 v2 이전 동작으로 되돌린다(읽기 지연 7.5 ms로 회귀하지만, 그것은 장애가 아니라
  성능이다).
- 가지치기 수정·fail-open·offheap/페이징 테스트는 **남긴다**.
- 이 상태로 41번에 배포해 격리를 해제한다. 여기가 재설계의 **기준선**이다.

## 2. 본 설계 — 배열에서 직접 스트리밍하는 읽기

### 2.1 구조

읽기 이터레이터가 컬럼 배열 위를 **직접 걷는다**. 스냅샷 개념 자체를 없앤다.

```
rowIterator(key, slices, reversed)
  └─ 샤드별 (가지치기 통과 시):
       StreamingRowIterator
         ├─ 열 때 1회: consolidate() — 미정렬 꼬리(≤1024) 접기, 락 안
         ├─ 열 때 1회: size S 캡처 (그 뒤 append 는 이 읽기에 안 보임 — 스냅샷과 같은 의미론)
         ├─ slices → 배열 이진 탐색으로 [from..to) 구간 결정   ← O(log n)
         ├─ 구간을 걸으며 행을 하나씩 조립해 yield             ← O(반환 행)
         │    슬롯이 superseded 면 건너뜀 (진실은 overflow 에)
         ├─ overflow(ConcurrentSkipListMap) 서브맵과 2-way 병합
         └─ 톰스톤 리스트·static 행은 기존 객체 경로로 병합
```

- **행 조립은 당겨질 때(per pull)**: `BTreeRow` 하나씩 만들어 넘긴다. 소비자가 어차피 요구하는
  할당이고, 파티션 전체 물질화가 없다. LIMIT·페이징이 당기기를 멈추면 조립도 멈춘다.
- **slices가 이진 탐색으로 내려간다**: v2의 스냅샷조차 못 주던 성질 — 슬라이스 읽기가
  O(파티션)이 아니라 O(log n + 구간 행 수)가 된다. 시간 범위 질의가 지배적인 워크로드에
  정확히 맞는 비용 모델이다.
- **보유 상태 0**: 이터레이터가 닫히면 아무것도 남지 않는다. OOM 벡터가 구조적으로 없다.

### 2.2 동시성 — 배열을 append-only 로 만든다

v2가 스냅샷을 쓴 진짜 이유는 "쓰기가 슬롯을 in-place 수정하므로 읽는 중에 찢어질 수 있다"였다.
해법은 스냅샷이 아니라 **in-place 수정의 제거**다:

| 지금 (in-place) | 재설계 (append-only) |
| --- | --- |
| 같은 클러스터링 재기록 → 슬롯 값 덮어씀 | 새 슬롯 append + 옛 슬롯에 `superseded` 플래그(volatile, 1회성) |
| 부분 UPDATE → 슬롯을 overflow로 승격하며 수정 | overflow(ConcurrentSkipListMap)에 넣고 옛 슬롯 `superseded` |

- 슬롯은 **append 후 불변**, 플래그만 0→1로 한 번 바뀐다. `size S`를 캡처한 리더는 각 슬롯을
  "살아있음" 또는 "superseded"로만 본다 — 찢어진 행이 존재할 수 없다.
- 리더는 락을 잡지 않는다(consolidate 순간 제외). 쓰기는 리더를 기다리지 않는다.
- 대가: 같은 셀을 재기록하면 슬롯이 하나 늘어난다. memtable은 flush까지만 사는 구조라
  누적은 유한하고, flush가 자연 청소다. 재기록이 병적으로 많은 파티션은 superseded 비율이
  임계(예: 50%)를 넘으면 그 파티션만 객체 계층으로 강등한다 — fail-open과 같은 원리.
- **읽기 도중 발생하는 promotion**: 리더가 슬롯을 읽는 시점과 플래그 확인 사이의 경합은
  "플래그 확인 → 행 조립 → 플래그 재확인, 바뀌었으면 overflow에서 다시"의 double-check로
  닫는다. overflow는 concurrent 구조라 락이 필요 없다.

### 2.3 명시적으로 하지 않는 것

- **스냅샷·캐시·보유 일체 없음** (제약 ③). "상한 있는 캐시"는 이 설계가 목표 미달일 때의
  다음 수단이지 1차 수단이 아니다.
- 질의 결과 의미론 변경 없음 — 차등 테스트(대 skiplist)가 계속 심판이다.
- `partitionIterator`(레인지 읽기) 최적화 없음 — 기존 범위 밖 유지.
- flush 경로 변경 없음 — `flushView()`는 이미 스트리밍이다.

## 3. 검증 — 게이트가 셋, 전부 실패에서 태어났다

| 게이트 | 내용 | 태생 |
| --- | --- | --- |
| **차등 + 뮤테이션** | 기존 45건 전부 무수정 통과 + supersede 경로 신규 케이스(재기록 중 읽기, 승격 중 읽기, DESC, 역순 도착). 각 신규 테스트는 뮤테이션으로 빨간불 증명 | 원래 규율 |
| **offheap + 네이티브 페이징** | `offheap_objects` 고정 클래스 + `executeNet` 페이징 — v1 재발 방지 | v1 장애 |
| **소크형 힙 테스트** | 다수 파티션에 쓰기·읽기를 **지속 교차**시키며 allocator `owns()`/jamm deep-size가 **평탄(plateau)한지** 단언. 상승 추세면 실패. 별도 long 테스트로 CI 야간 배치 | v2 OOM |
| 성능 실측 | 재구축 카운터 대신 **읽기당 조립 행 수 카운터** — slices 읽기가 구간 행 수만 조립하는지. 벽시계 금지 | 원래 규율 |

**롤아웃 게이트**: 위 전부 초록 → 41번 배포 → **힙 추세를 6시간 이상 관찰**(모니터의 힙 필드가
톱니(진동)를 유지하는지 — v2는 6시간 뒤에야 죽었다) → 그 뒤에만 "완료" 선언.

## 4. 구현 순서

| # | 내용 | 게이트 |
| --- | --- | --- |
| 0 | master 격리 해제 (스냅샷 보유 제거, §1) | 기존 45건 + 41번 배포로 기준선 복원 |
| 1 | append-only 슬롯 + supersede 플래그 (쓰기 경로) | 차등 무수정 통과, supersede 뮤테이션 |
| 2 | StreamingRowIterator (읽기 경로) | 차등 + offheap/페이징 + 조립 행 수 카운터 |
| 3 | 소크 힙 테스트 + 야간 CI 배선 | 평탄 단언 통과 |

1과 2는 분리 배포 가능하다 — 1만 들어가도 동작은 오늘과 동일하고(읽기는 여전히 재구축),
2가 실제 성능을 가져온다. v2의 교훈대로 **한 번에 하나씩** 프로덕션을 통과시킨다.
